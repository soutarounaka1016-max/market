# Codex長時間タスク実行プロトコル

このファイルは、`tasks/active-task.md` の作業を途中で放棄しにくくするための実行ルールです。`active-task.md` と同時に読み、こちらを作業継続ルールとして適用してください。

## 1. 基本原則

- 計画、調査、説明だけで終了しない。
- `tasks/active-task.md` の完成条件を満たすまで、実装、テスト、修正、再テスト、文書更新を繰り返す。
- 1つのフェーズが終わったら停止せず、直ちに次の未完了フェーズへ進む。
- ユーザーへの途中確認が不要な軽微な判断は、自律的に決定する。
- 時間がかかること自体を停止理由にしない。
- 作業量が多い場合も、実装範囲を勝手に縮小して「完了」と扱わない。

## 2. 開始時に行うこと

作業開始時に、内部で次のチェックリストを作成してください。

- [ ] フェーズ0
- [ ] フェーズ1
- [ ] フェーズ2
- [ ] フェーズ3
- [ ] フェーズ4
- [ ] フェーズ5
- [ ] フェーズ6以降
- [ ] 全テスト
- [ ] 自己レビュー
- [ ] PRODUCT_SPEC.md更新
- [ ] PROGRESS.md更新
- [ ] README.md更新
- [ ] mainの最新状態との同期
- [ ] コンフリクト確認と解消
- [ ] Pull Request作成

`active-task.md` に別のフェーズ構成がある場合は、その構成に合わせてチェック項目を追加・修正してください。

## 3. 各フェーズの完了条件

各フェーズは、次のすべてを満たしたときだけ完了扱いにしてください。

1. 現在のコードを確認した。
2. 必要な実装を行った。
3. 構文または静的確認を行った。
4. 対象機能のテストを行った。
5. テスト失敗があれば原因を修正した。
6. 再テストした。
7. 既存主要機能への影響を確認した。

コードを書いただけ、テストを書いただけ、文書を書いただけでは完了ではありません。

## 4. 問題が起きた場合

1つの項目で問題が起きても、プロジェクト全体を直ちに停止しないでください。

次の順で対応してください。

1. 原因を調査する。
2. 少なくとも2つの現実的な解決方法を検討する。
3. 最も単純で安全な方法を実装する。
4. テストする。
5. それでも解決できない場合は、未解決事項として記録する。
6. その問題に依存しない別のフェーズや作業を続行する。

外部ネットワークが使えない場合も、モック、純粋関数テスト、構文確認、静的確認、既存データを使ったテストを進めてください。ネットワーク確認不能だけを理由に全作業を停止しないでください。

## 5. 停止してよい条件

次のいずれかの場合だけ、完成前の停止を認めます。

- APIキー、パスワード、秘密情報が不可欠である。
- 有料サービスへの契約が不可欠である。
- 保存済みデータを失う重大な変更について、ユーザー判断が必要である。
- 法律、規約、個人情報に関する重大な判断が必要である。
- リポジトリや実行環境が壊れており、合理的な代替手段でも作業不能である。

停止する場合も、次を必ず行ってください。

- 完了済み項目を記録する。
- 未完了項目を具体的に記録する。
- 停止理由を証拠とともに説明する。
- 再開に必要な操作を1つずつ示す。
- 可能な範囲のテストと文書更新を終える。

「作業が大きい」「時間がかかる」「追加確認が望ましい」は、それだけでは停止理由になりません。

## 6. コンテキスト節約

- 同じ説明を何度も書かない。
- 読み終えたファイルを不必要に再読しない。
- 大量のコードを無目的に表示しない。
- 変更対象を先に特定してから編集する。
- テスト結果は要点を記録し、冗長なログを最終報告へ貼りすぎない。
- フェーズ完了時に短い内部要約を残し、次へ進む。

## 7. Pull Requestの自動作成

実装とテストが完了したら、ユーザーに「PRを作りますか」と確認せず、自動的にPull Requestを作成してください。

Pull Request作成前に必ず次を行ってください。

1. リモートの `main` の最新状態を取得する。
2. 作業ブランチへ最新の `main` を取り込む。
3. コンフリクトの有無を確認する。
4. コンフリクトがなければ全テストを再実行する。
5. コンフリクトがあれば、次章の手順で解消する。
6. 解消後に構文確認、テスト、差分確認を再実行する。
7. 変更をコミットして作業ブランチへpushする。
8. タイトル、変更内容、テスト結果、制限、実機確認項目を含むPull Requestを作成する。

Pull Requestの本文には、少なくとも次を含めてください。

- 目的
- 実装内容
- 変更ファイルの概要
- 実行したテストと結果
- 自動確認できなかった項目
- iPadまたは公開環境で人間が確認すべき項目
- 既知の制限

PR作成に失敗した場合は、原因を確認し、GitHub接続、ブランチ名衝突、push失敗、権限不足など、修正可能な原因を自律的に修正して再試行してください。

## 8. コンフリクトの自動解消

Pull Request作成前または作成後に `main` とのコンフリクトが発生した場合、ユーザーへ直ちに丸投げせず、まず自動解消を試みてください。

### 解消手順

1. 最新の `main` と作業ブランチの両方の変更意図を確認する。
2. コンフリクトしたファイルだけでなく、関連コードと管理文書も読む。
3. 単純に `ours` または `theirs` を一括採用しない。
4. 両方の有効な変更を残し、重複実装、重複DOM、重複イベント登録、未定義参照を作らない形に統合する。
5. `<<<<<<<`、`=======`、`>>>>>>>` が残っていないことを確認する。
6. JavaScript構文、重複ID、未定義関数・変数、submitイベント重複、文書とコードの不一致を確認する。
7. 全テストを再実行する。
8. 解消コミットをpushし、Pull Requestがマージ可能な状態か再確認する。

### 自動解消を中止してよい場合

次の場合だけ、人間の判断が必要として停止してください。

- どちらの仕様を正式採用するかで利用者体験が大きく変わる。
- 保存データ形式の互換性を壊す選択が必要である。
- 主要機能を削除する判断が必要である。
- 両方の変更意図が矛盾し、文書やコードから正解を判断できない。

その場合も、単に「コンフリクトがあります」とだけ報告せず、次を示してください。

- 対象ファイル
- 衝突している2つの変更意図
- 推奨案
- 代替案
- 各案の影響
- ユーザーが選ぶべき最小限の質問

## 9. PR作成後の再同期

PR作成後に `main` が更新されてマージ不能になった場合は、可能なら同じ作業内で次を行ってください。

1. 最新の `main` を取得する。
2. 作業ブランチへ取り込む。
3. コンフリクトを自動解消する。
4. テストを再実行する。
5. 修正をpushして既存PRを更新する。

新しいPRを重複作成しないでください。既存PRのブランチを更新してください。

## 10. 最終確認

Pull Request作成前に、次を確認してください。

- [ ] `active-task.md` の全必須要件を確認した。
- [ ] 未実装項目を完成済みと記載していない。
- [ ] JavaScriptの構文エラーがない。
- [ ] 利用可能な自動テストが通る。
- [ ] 主要な既存機能を壊していない。
- [ ] localStorageの旧データ互換性を確認した。
- [ ] 外部文字列とURLを安全に扱っている。
- [ ] iPad幅で致命的な崩れがない。
- [ ] PRODUCT_SPEC.md、PROGRESS.md、README.mdが実装と一致する。
- [ ] 最新のmainを取り込み済みである。
- [ ] コンフリクトマーカーが残っていない。
- [ ] 人間が実機確認すべき項目を明記した。

## 11. 最終成果物

最終的に次を作成してください。

1. 完成した実装
2. テスト
3. 更新済み管理文書
4. 最新のmainと同期され、コンフリクトを解消した作業ブランチ
5. 変更内容、テスト結果、制限、実機確認項目を含むPull Request

Pull Requestを作成し、可能な範囲でマージ可能な状態にするまで、通常の完了とは扱わないでください。
