# 社会ニーズ発見レーダー：候補選別・整理・バックアップ機能

AGENTS.md、PRODUCT_SPEC.md、PROGRESS.md、README.md、および現在のmainブランチのコード全体を確認してください。過去のPR説明ではなく、現在のコードを唯一の事実として扱ってください。

## 目的

現在取得できるGitHub IssuesとHacker Newsの候補を、単に大量表示する一覧から、検索・絞り込み・並べ替え・分類・保存・バックアップができる候補選別ワークスペースへ発展させてください。

計画だけ、調査だけ、または1機能だけで停止せず、以下のフェーズを順番に進めてください。各フェーズで、現状確認、実装、テスト、不具合修正、再テスト、進捗記録を行ってください。重大な停止理由がない限り、最終完成条件を満たすまで継続してください。

軽微な技術判断は質問せず、既存設計と一貫し、単純・安全・元に戻しやすい方法を選んでください。APIキー、有料サービス、保存済みデータの破壊、重大な規約問題が必要な場合だけ停止し、理由・完了済み項目・未完成項目・再開方法を報告してください。

# フェーズ1：候補の検索・絞り込み・並べ替え

取得済み候補に対して、次を実装してください。

## 検索

タイトル、本文、投稿者、タグ、情報源名、リポジトリ名などを対象に検索できるようにしてください。大文字小文字を無視し、前後空白を除去し、検索欄が空なら全件表示してください。

## 絞り込み

- 情報源：すべて / GitHub Issues / Hacker News
- 保存状態：すべて / 未保存のみ / 保存済みのみ
- 最低コメント数
- 最低スコアまたはポイント

初期状態は未保存のみを優先してください。不正な数値は安全に補正するか、日本語でエラー表示してください。

## 並べ替え

- 課題らしさが高い順
- 新しい順
- コメント数が多い順
- スコアまたはポイントが高い順
- 取得した順

同点時にも順番が不規則に変わらない安定した並べ替えにしてください。

## 表示と操作

- 取得総数
- 絞り込み後の件数
- 未保存件数
- 保存済み件数
- 条件リセット
- 現在の取得結果を消去
- 保存済み候補を一時的に非表示

一括保存は実装しないでください。

# フェーズ2：透明な「課題らしさ目安」

AI APIを使わず、説明可能なルールで0〜100点の「課題らしさ目安」を計算してください。これは事業性、収益性、成功確率ではありません。画面上でもそのように明記してください。

候補カードには、点数だけでなく、主な加点理由と減点理由を最大3〜5件表示してください。

## GitHub Issuesの材料例

加点：具体的な本文、再現手順、複数コメント、bug/problem/help wanted/enhancement系ラベル、困りごとや要望を示す語。

減点：本文なし、極端に短い、依存関係更新だけ、バージョン更新だけ、リリース作業、内部管理、単なる質問や告知。

## Hacker Newsの材料例

加点：Ask HN、困りごと・不便・失敗・代替手段への不満、具体的本文、コメント数が多い、同じ悩みを持つ人を募る内容。

減点：単なる製品発表、技術ニュース、求人、宣伝、本文なし、一般ニュース、Show HNで製品紹介中心。

キーワード1個だけで極端な高得点にならないようにしてください。計算処理はDOMから分離した純粋関数にし、重みは定数として整理してください。点数は0〜100に収めてください。

# フェーズ3：Hacker News取得品質の改善

現在使用しているAPIの正式な仕様を確認し、推測で存在しないパラメータを作らず、可能な範囲で次を実装してください。

- 取得件数：10 / 20 / 30 / 50件、初期値20
- 取得順：新しい順 / 関連度または人気順。APIで正確に対応できる場合のみ
- 投稿種別：すべて / Ask HN / Show HN。APIで正確に対応できる場合のみ
- 検索例を表示し、押すと入力欄へ設定される。勝手に通信は開始しない
- Ask HN、Show HN、通常投稿の種別表示
- 本文の省略
- 投稿者、コメント数、投稿日、ポイントの整理
- 本文がないことの明示
- 元記事URLとHacker News投稿URLが両方ある場合の区別

外部HTMLを無加工でinnerHTMLへ挿入しないでください。

# フェーズ4：保存済み課題の整理

各保存済み課題へ次を追加してください。

## 検討状態

- 未確認
- 有望
- 保留
- 除外

初期値は未確認。古いデータも未確認として安全に扱ってください。変更後はlocalStorageへ保存してください。

## 自分用メモ

外部原文とは別に、日本語で要約、気になった理由、追加調査、想定利用者、解決案の仮説を書けるようにしてください。

## 手動タグ

カンマ区切りなどiPadで入力しやすい方法にしてください。重複タグ、前後空白、空タグを正規化してください。

## 保存済み課題の検索・絞り込み・並べ替え

絞り込み：状態、情報源、手動タグ、キーワード、課題らしさ目安。

並べ替え：登録が新しい順、更新が新しい順、課題らしさ順、状態別、タイトル順。初期状態は更新が新しい順。

保存済み課題には、タイトル、状態、情報源、課題らしさ目安、タグ、メモ、登録日、更新日、編集、削除、元ページを表示してください。保存前候補とは視覚的に明確に分けてください。

# フェーズ5：JSONバックアップと復元

保存済み課題をJSONへ書き出し、JSONから安全に追加・統合できるようにしてください。

## 書き出し形式

```javascript
{
  schemaVersion,
  exportedAt,
  appName,
  needs
}
```

ファイル名には日付を含めてください。取得候補の一時データは含めず、保存済み課題だけを対象にしてください。

## 読み込み

読み込み前にJSON解析、形式、needs配列、各課題の最低限のタイトル、ファイルサイズを検証してください。不正データでアプリが停止しないようにしてください。

読み込み前に、対象件数、新規追加件数、重複件数、不正件数を表示し、確認後に追加・統合してください。

重複判定は、ID、sourceTypeとexternalId、sourceUrl、タイトルと作成日時の完全一致を利用してください。

現在の`marketNeeds.v1`を維持し、古いデータで次の項目がなくても正常動作させてください。

- reviewStatus
- userMemo
- userTags
- problemSignalScore
- problemSignalReasons
- sourceType
- sourceUrl
- externalId
- fetchedAt

# フェーズ6：エラー処理

少なくとも次を日本語で表示してください。

- 検索条件・数値入力が不正
- API通信失敗・利用制限・0件
- localStorage読み込み・保存失敗
- JSON未選択、解析失敗、形式不正、サイズ過大
- 読み込める課題が0件
- 全件重複
- 書き出し失敗

成功、警告、失敗を文章でも区別し、色だけに依存しないでください。通信中は進行表示、ボタン無効化、二重送信防止を行い、完了後に戻してください。可能ならAbortControllerでタイムアウトを実装してください。
